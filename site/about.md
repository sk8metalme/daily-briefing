## 何をしているサイトか

Claude Code のクラウド routine（スケジュール実行エージェント）が **毎朝 06:30 JST** に無人で起動し、
以下のトピックについて世界中の新着ブログ記事・研究・実践レポートを調査して、3 件を選び、
全文日本語のブリーフィングを書いて GitHub へコミットします。このサイトはその蓄積ログを読みやすく配信したものです。

- AI-Ready、そして AI-Ready の次にやるべきこと
- SDD / AI-DLC その他の AI 開発フローフレームワーク
- 組織を AI ネイティブにする方法
- 開発ワークフロー全体への AI 活用（リリースまでのリードタイム短縮）
- jev の活用

## 選定基準

**実業務で再現可能な実践知を最優先**します。単なるニュース、製品発表のみの記事、宣伝記事は除外します。
具体的な手法・設定・コード・運用ノウハウが含まれるものを優先し、
**必ず記事本文を取得して読んでから**選定・執筆します（検索結果のスニペットだけでは書きません）。

過去に選定した記事は[記事インデックス](articles.html)で一元管理し、
URL が違っても実質同一内容（転載・翻訳版・同一発表の別報道）は重複として弾いています。

## 各記事に書いていること

| セクション | 内容 |
|---|---|
| 本文翻訳 | 原文の論旨の流れ・構成を保った日本語訳（最大 2000 字程度に圧縮） |
| 重要ポイント | 3〜5 点の要約 |
| 図解 | 仕組み・処理フロー・構成要素の関係を図示 |
| 戦略分析 | ビジネスフレームワークによる構造化（後述） |
| 現場での適用方法 | そのままコピーして使える CLAUDE.md / SKILL.md / スクリプトの実物 |
| 期待効果 | 適用した場合に期待できる効果（記事中の数値を引用） |
| 注意点 | 落とし穴・前提条件・制約 |

## 図解の方針

図は「意図」に合わせて 2 つの形式を使い分けます。

- **Mermaid** — 処理フロー・シーケンス・状態遷移など、**手順や時間順序**が主題のとき。
  GitHub の Markdown 上でもそのまま描画されるため、更新頻度の高い内容に向いています。
- **インライン SVG** — 比較マトリクス・四象限・Wardley マップ・階層スタック・ファネルなど、
  **位置関係そのものが意味を持つ**とき。Mermaid の自動レイアウトでは表現できないため、
  [diagram-design](https://github.com/cathrynlavery/diagram-design)（MIT, Cathryn Lavery）の
  設計規範に沿って手で描き起こします。

後者の設計規範（ノード上限 9・アクセント 1 色・影を使わず 1px ヘアライン・4px グリッド・
直交コネクタのみ）は、このサイト自体の配色・余白設計にもそのまま適用しています。

## 戦略分析の方針

記事の内容に応じてビジネスフレームワークを 1〜2 個選び、
「この記事の主張を自社に当てはめると何が意思決定として変わるか」まで書きます。
バリューストリームマッピング、制約理論、Wardley マップ、JTBD、SWOT/TOWS、
ファイブフォース、ケイパビリティ成熟度、Cost of Delay などから、
記事の論点に対して最も情報量が増えるものを選びます。
フレームワークを当てはめること自体が目的にならないよう、
**「結局どう動くか」の示唆**を必ず伴わせています。

## このサイトの作り

- ブリーフィング本体は `briefings/YYYY/MM/DD.md`。front matter を持たない素の Markdown です。
- `site/build.py`（Python + `markdown` のみ）が静的 HTML を生成し、GitHub Actions が Pages へデプロイします。
- ブリーフィングの書式を変えずにサイトを作れるよう、ジェネレータ側が Markdown を解析しています。
  routine 側の書き込み規約は変わりません。

ソースは [github.com/sk8metalme/daily-briefing](https://github.com/sk8metalme/daily-briefing) にあります。
