# 戦略分析

## 目的

技術記事を「読んだ」で終わらせず、**意思決定の材料**に変換する。
このセクションの合格条件はひとつ: 読んだ人が **次に何を変えるか／変えないか** を言えるようになること。

フレームワークは思考の型であって目的ではない。当てはめること自体に価値はない。
**情報量が増えないならフレームワークを使わない。**「戦略分析省略（理由: 単一ツールの設定手順のため、組織的な意思決定に接続しない）」と書いてよい。

## 1. フレームワークを選ぶ

記事の型から選ぶ。**1記事につき1〜2個まで。** 3つ以上並べると分析が薄くなる。

| 記事の型 | 第一選択 | 併用候補 |
|---|---|---|
| リリースまでのリードタイム短縮、ワークフロー改善 | **バリューストリームマッピング** | 制約理論（TOC） |
| 「AI でコードは速くなったが○○が詰まる」系 | **制約理論（TOC）** | VSM、待ち行列 |
| AI-Ready、その次の段階、組織の成熟度 | **ケイパビリティ成熟度モデル** | Three Horizons |
| 組織を AI ネイティブにする、役割・体制の変更 | **マッキンゼー 7S** | ADKAR、RACI |
| SDD / AI-DLC など開発手法フレームワーク | **JTBD（Jobs to be Done）** | Cynefin |
| 人とエージェントの責務分担 | **RACI** | 権限分離の原則 |
| 計測・評価・メトリクス | **DORA Four Keys** | Goodhart の法則への反証 |
| ツール選定、内製 vs 外部調達 | **Make/Buy と TCO** | ファイブフォース |
| エコシステム動向、どの技術が標準になるか | **Wardley マップ** | 技術採用ライフサイクル |
| 何から着手するかの優先順位 | **Cost of Delay / WSJF** | ICE・RICE |
| 投資判断、コスト対効果 | **単位経済性（ユニットエコノミクス）** | 実オプション |
| どの業務をエージェントに任せるか | **Cynefin** | リスク×可逆性マトリクス |

迷ったら **バリューストリームマッピング + 制約理論**。このリポジトリが扱う記事の大半は
「開発プロセスのどこが詰まっていて、AI をどこに当てるか」という話に還元できる。

## 2. 出力テンプレート

````markdown
### 戦略分析

**フレームワーク**: バリューストリームマッピング × 制約理論

| 工程 | 作業時間 | 待ち時間 | 記事の主張 |
|---|---|---|---|
| 要件定義 | 2日 | 1日 | エージェントが曖昧さ検出で短縮 |
| 実装 | 3日 | 0 | **8割削減**（記事の数値） |
| コードレビュー | 0.5日 | **4日** | 短縮されない（人間がボトルネック） |
| デプロイ | 0.1日 | 0 | 変化なし |

**制約**: 実装が速くなるほどレビュー待ちの行列が伸びる。
記事が「レビュー可能な速度を超えて変更が生産される」と書いているのはこの状態を指す。
フロー効率は実装の高速化ではなく、**レビューのスループット**で決まる。

**示唆**: 実装支援ツールの追加投資よりも先に、レビュー工程に手を入れる意思決定が先行する。
具体的には (1) 変更粒度を小さくして1件あたりのレビュー時間を下げる、
(2) 検証エージェントで機械判定可能な指摘を事前に潰す、(3) レビュー担当を増やす、のいずれか。
記事は (1)(2) を推しており、(3) は制約を動かすが固定費が増える。

**反証条件**: レビュー待ち時間が実測で短い組織（レビュアーが潤沢、または trunk-based で
レビュー自体が非同期でない）ではこの分析は成立せず、別の工程が制約になる。
````

### 必須の4要素

1. **フレームワーク名** — 何を使ったか明示する
2. **構造化した中身** — 表か箇条書き。記事の記述・数値に基づくこと
3. **示唆** — 「だから意思決定がこう変わる」。ここが無い戦略分析は不合格
4. **反証条件** — この分析が成立しない前提は何か

## 3. 守ること

- **記事に書かれている事実・数値を根拠にする。** 記事に無い数値を作らない。
  一般的な相場観を使う場合は「一般には〜」と断り、記事の主張と区別する
- 記事がデータを示していない場合は、**仮説であることを明示する**
  （例: 「記事は定性的な記述にとどまるため、以下は仮説」）
- **示唆は具体的な動作に落とす。** 「組織的な取り組みが重要」は示唆ではない。
  「レビュー担当を増やすのではなく、変更粒度を下げる方を先に試す」が示唆
- 日本語で書く。フレームワーク名は原語のままでよい
- **分量は 400〜800 字程度。** 本文翻訳より長くしない

## 4. やってはいけないこと

- フレームワークを**名前だけ**出して中身を埋めない（「SWOT で整理すると〜」とだけ書く）
- SWOT の4象限を無理に全部埋める。空の象限は「該当なし」と書く方が誠実
- 記事が1つのツールの使い方だけを説明しているのに、無理に業界構造を論じる
- 複数のフレームワークを並べて、どれも浅い状態にする
- 記事への賛同だけを書く。**記事の主張が通らない条件**を必ず1つは挙げる
- 一般論の水増し（「AI 活用は今後ますます重要になる」の類）

## 5. 主要フレームワークの最小限の使い方

**バリューストリームマッピング**: 工程を分解し、各工程の *作業時間* と *待ち時間* を分けて置く。
フロー効率 = 作業時間合計 ÷ リードタイム。多くの組織で 5〜15%。改善余地は待ち時間側にある。

**制約理論（TOC）**: (1) 制約を見つける (2) 制約を徹底活用する (3) 他を制約に従属させる
(4) 制約を引き上げる (5) 繰り返す。**制約以外の改善はリードタイムを縮めない**のが要点。

**ケイパビリティ成熟度**: 段階（例: 個人利用 → チーム規約 → パイプライン統合 → 自律運用）を
置き、各段階の *完了条件* を書く。「次に何をすれば次段階か」が言えないモデルは使わない。

**Wardley マップ**: 横軸に進化段階（Genesis / Custom / Product / Commodity）、
縦軸に可視性（ユーザーから見える度合い）。コモディティ化しつつある構成要素への内製投資は
回収できない、という判断に使う。

**JTBD**: 「この手法は、どんな状況で、何を片付けるために雇われるか」。
機能ではなく状況で定義する。既存の代替手段（今は何でその仕事を片付けているか）を必ず書く。

**DORA Four Keys**: デプロイ頻度 / 変更のリードタイム / 変更失敗率 / 平均復旧時間。
速度2指標と安定性2指標の **両方** を見る。片方だけの改善主張は疑う。

**RACI**: Responsible（実行）/ Accountable（説明責任）/ Consulted / Informed。
人とエージェントの分担を論じる記事では、**Accountable は人間から動かせない**点が常に論点になる。

**Cynefin**: 明白 / 煩雑 / 複雑 / カオス。明白・煩雑はエージェントに委譲しやすく、
複雑は「探索 → 感知 → 対応」なので人間の判断が要る。委譲範囲の線引きに使う。

**Cost of Delay / WSJF**: WSJF = 遅延コスト ÷ 作業規模。
「全部やる」を避け、順序を決める根拠にする。遅延コストは記事の数値から見積もる。
